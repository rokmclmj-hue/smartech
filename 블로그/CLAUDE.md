# 블로그 글 작성 자동화 시스템

사용자가 선택하고 작성 승인한 주제를 리서치 → 글쓰기 → 이미지 → 검수 순서로 처리한다. 신규 글은 Astra 중심으로 제작하며 기존 단계별 지침과 검증을 유지한다. 후보 제시는 작성·예약·업로드 승인을 대신하지 않는다.

---

## 업로드 주기 — 월·목 주 2편 (2026-09-09 승인)

- **2026-09-14부터 월·목 주 2편**: day1=월요일, day2=목요일, 09:00 한국시간.
- 2026-08-05의 50편 전환 계획을 사용자의 이번 승인에 따라 시행한다. 로컬 final.md 개수·작성완료 이력·홈페이지 공개 글 수·검색 색인 수는 서로 다르다.
- 이번 금요일 **0911-아웃가스-원리**는 **9/11 사용자 업로드 요청을 기다린다**. 자동 승인·미리 발행하지 않는다.
- 자동 실행은 `auto_upload.py`의 정확한 발행일·큐 주차·승인 검사를 거친다. 9/14 이후 day3와 임시 day4·day5는 사용하지 않는다. `--force` 우회는 차단된다.
- `setup_scheduler.ps1`은 월·목 작업을 준비하고 기존 수·금·임시 작업을 백업 후 비활성화한다. 실제 등록 여부는 작업 스케줄러와 작업 로그에서 확인하며 문서만 바꾸고 적용됐다고 보고하지 않는다.
- 예약일에 컴퓨터가 꺼져 날짜가 지나갔다면 자동 발행하지 않는다. 누락 글은 사용자와 새 날짜를 정한다.

## 주제 선정 모드

사용자가 "주제 뽑아줘", "이번 주 주제 추천해줘", "다음주 주제 후보" 등을 요청하면
**기본 후보 5개(제목 + 이유 한 줄)를 제안하고, 사용자가 2개를 선택한 뒤 글 작성을 시작한다.** 요청한 후보 수가 따로 있으면 그 수를 따른다.

---

### 핵심 구조: 20 산업 × 5 제품 = 100개 주제 매트릭스

산업군 20개를 순환하며, 각 산업에서 5가지 제품 카테고리 중 1개를 선정한다.
전체 목록은 `블로그/knowledge/industry-product-matrix.md` 참고.

**5가지 제품 카테고리:**
- A. 드라이펌프 — 이 산업에 적합한 드라이펌프 선택 가이드
- B. 오일로터리펌프 — 오일식 진공펌프 적용 및 관리
- C. 진공게이지 — 측정범위와 게이지 종류 선택
- D. 오일/소모품 — 교환주기, 오일 선택, 소모품 관리
- E. 부품/배관 — 플랜지·밸브·호스·피팅 선택 기준

---

### 1단계 — 현재 로테이션 위치 확인

`블로그/knowledge/topic-tracker.json`을 읽는다.
- `current_industry_index`: 다음에 선정할 산업군 번호 (1~20)
- `used_consultation_records`: 이미 사용한 상담기록 파일명 목록
- `completed_topics`: 이미 작성 완료된 주제 목록. 홈페이지 발행 완료를 뜻하지 않는다.
- 트래커·산업 매트릭스·실제 원고 폴더를 대조한다. 누락된 기존 원고는 작성완료 이력으로만 보완하고 발행 상태를 추측하지 않는다.
- 후보 검토만으로 새 completed_topics 항목, 순환 인덱스, 상담기록 사용 이력을 변경하지 않는다.

---

### 2단계 — 후보 5개 생성

아래 기준을 적용해 후보 5개를 만든다.

**① 산업군 로테이션** (`industry-product-matrix.md` 참고)
- `current_industry_index`부터 시작해 미완료 칸을 순서대로 선정한다.
- 이미 완료된 칸(산업 + 제품 조합)은 건너뛴다.
- **주제 균형**: 후보 5개 중 1개는 일반 진공이론·안전 주의사항으로, 나머지는 산업별 주제로 구성한다. 다른 후보 수를 요청받아도 일반 주제 1개 정도를 포함한다.
- "공통" 주제를 생성해도 `current_industry_index`는 변경하지 않는다. 특정 산업군 주제가 완료됐을 때만 인덱스를 앞으로 진행한다.

**② 키워드 검색량** (`data/keyword_map.csv`)
- 조사일·출처·CSV 열 정합성이 확인된 검색량만 수치로 인용한다. 현재 파일의 천단위 쉼표·조사일 누락을 먼저 확인한다.
- 유효한 수치가 없으면 검색 의도·제품 관련성·기존 내용과의 차이로 선정하고 최신 검색량이라고 단정하지 않는다.

**③ 상담기록 참조** (`data/상담기록/`)
- `used_consultation_records`에 없는 파일 중 주제와 관련된 것을 1개 연결한다.
- 상담기록이 없어도 주제 선정은 가능하다 (절대적 기준 아님).
- 원고에 실제 반영한 상담기록은 작성완료 후 담당자가 `topic-tracker.json`에 기록한다. 후보 검토나 자료 열람만으로 소모 처리하지 않는다.

**④ 중복 방지** (`블로그/output/` 폴더)
- 이미 작성된 글과 산업군 + 제품 카테고리가 동일하면 제외한다.
- 제목·핵심 질문·본문 구성·추천 제품이 겹치는지 인접 원고를 직접 대조한다. 수치로 유사도를 측정하지 않았다면 “80%”처럼 측정값을 꾸며내지 않는다.
- 일반 주제도 기존 글의 일부 내용을 제목만 바꾼 반복이면 제외하고, 새롭게 답할 질문을 기록한다.

**⑤ 현장사진 가용성** (`data/현장사진/` 폴더)
- 해당 산업·제품 관련 현장사진이 있으면 후보 표시에 📷 마크 추가.

---

### 3단계 — 주제 후보 표시

```
블로그 주제 후보 5개 — 대상: YYYY-MM-DD(월), YYYY-MM-DD(목)

① [제목 후보]
   이유: [선정 이유 한 줄]

②~⑤ [같은 형식]

2개를 선택해 주시면 해당 주 월·목 원고를 작성합니다.
```

### 4단계 — 사용자 선택 후 작성, 완료 후 이력 기록

1. 사용자가 고른 2개 주제와 날짜를 기록한 뒤 Step 1~4를 순서대로 진행한다. 선택만으로 발행이나 예약 승인을 기록하지 않는다.
2. 원고 작성·검수 완료 후 `completed_topics`에 작성완료를 기록하고, 실제 사용한 상담기록만 `used_consultation_records`에 추가한다.
3. 완료한 산업별 글에 대해서만 `current_industry_index`를 갱신한다. 공통 글로는 이동하지 않는다. 한 담당자만 트래커·큐를 수정한다.
4. 원고·사진 승인과 예약/즉시발행 요청을 구분해 아래 단계로 진행한다.

## 현장사례 모드

### "현장사례 등록해줘" 트리거 — 파일 자동 감지

사용자가 **"현장사례 등록해줘"** 라고 하면:

1. `C:\Users\rokmc\Desktop\` 에서 아래 패턴 파일을 스캔한다.
   - `납품사진_*` — 납품 케이스
   - `수리사진_*` — 수리 케이스
2. **파일명 규칙**: `납품사진_날짜_업체명_제품_내용_번호.jpg`
   - 예: `납품사진_20260622_희성촉매_TStation85D_연구용분석장비_1.jpg`
   - 사진이 1장이면 번호 생략 가능
3. `블로그/data/cases/` 이미 등록된 폴더와 대조해 **신규 케이스만** 처리한다.
4. 신규 케이스 발견 시:
   - 폴더 자동 생성: `YYYYMMDD_구분_이니셜_제품명`
   - 사진 자동 복사 (photo1.jpg, photo2.jpg …)
   - `info.txt` 자동 생성 (파일명에서 추출, 업체 실명 포함)
5. 완료 후 "글 써드릴까요?" 물어본다. 사용자 확인 후 글 작성 시작.

> **업체 실명 보안**: info.txt의 업체명은 리서치에만 사용. 생성된 글·DB·파일 어디에도 실명 기재 금지.

### "현장사례 써줘" 트리거 — 글 생성

사용자가 **"현장사례 써줘"** 또는 **"현장사례 글 써줘"** 라고 하면 아래 단계를 실행한다.

### Step 0 — 미발행 케이스 감지

`블로그/data/cases/` 폴더를 스캔한다.
- `_템플릿_` 으로 시작하는 폴더/파일은 건너뛴다.
- 각 케이스 폴더의 `info.txt`를 읽어 `발행: false` 인 항목을 모두 나열한다.
- 미발행 케이스가 여러 개면 사용자에게 목록을 보여주고 선택하게 한다.
- 미발행 케이스가 1개면 바로 진행한다.

### Step 1 — 케이스 파일 읽기

선택된 케이스 폴더에서:
- `info.txt` 읽기 (날짜, 구분, 업체, 이니셜, 제품, 공정, 메모, 사진블러 확인)
- 폴더 내 사진 파일 목록 확인 (photo1.jpg, photo2.jpg 등)
- **업체 실명은 리서치에만 사용하고, 글 본문·파일·DB에는 절대 기재하지 않는다**

### Step 2 — 업종 리서치 (WebSearch 사용)

`info.txt`의 업체명과 공정 정보를 바탕으로:
1. 업체 홈페이지 검색 → 어떤 공정에서 진공펌프를 쓰는지 파악
2. 동종업계 공정 일반 정보 검색 (업체 특정 없이 공정 일반화)
3. 해당 공정에 납품된 제품(T-Station 85D, E2M1.5 등)의 적합성 근거 정리
4. 산출물: `블로그/output/납품사례(또는 수리사례)/YYYY-MM/YYYYMMDD-이니셜-제품명/research.md`

> **폴더명 규칙**:
> - 납품: `output/납품사례/2026-06/20260622-H사-TStation85D/`
> - 수리: `output/수리사례/2026-06/20260622-G사-iH1800/`
> - 날짜를 앞에 배치해 파일 탐색기에서 날짜순 자동 정렬

### Step 3 — 글쓰기 (writer.md 규칙 준수)

`블로그/agents/writer.md` 규칙을 따르되, 현장사례 전용 추가 규칙 적용:
- **카테고리**: `현장사례`
- **태그**: 구분(납품/수리/오버홀) + 제품명 + 공정명 포함
- **업체 표기**: 업체명·이니셜 모두 사용 금지. 공정 중심으로 서술 (예: "귀금속 촉매 성능 분석 공정에 납품"). 재언급 시 "해당 연구소에는"으로 대체
- **글 구성**:
  1. 도입: 어떤 공정에 어떤 문제/필요가 있었는지
  2. 제품 선정 이유: 왜 이 제품이 이 공정에 맞는지 (기술적 근거)
  3. 납품/수리 결과: 설치·테스트 완료, 성능 확인
  4. 마무리: 동종 공정을 운영하는 독자에게 연결
- **사진 사용**: `info.txt`의 사진블러 값 확인
  - `불필요` → photo1.jpg, photo2.jpg 그대로 사용 (thumbnail 용도)
  - `필요` → blur_photo.py 처리 후 사용

### Step 4 — 품질 검수 (check_quality.py)

기존 파이프라인과 동일하게 실행.

### Step 4.5 — 사진 승인

사진 표시 후 사용자 OK 받기.

### Step 5 — 발행 및 info.txt 업데이트

발행 완료 후 `info.txt`의 `발행: false` → `발행: true` 로 변경.

## 사용자가 주제를 주면 따라야 할 단계

**Step 1 — 리서치** (`블로그/agents/research.md`)
- 산출물: `블로그/output/기술블로그/YYYY-MM/MMDD-짧은제목/research.md`
- **폴더명 규칙**: `기술블로그/` 아래 월별 폴더(YYYY-MM), 그 안에 `MMDD-짧은제목` 형식으로 생성. 상위 폴더에 연·월이 이미 있으므로 폴더명에는 일(MMDD)만 붙이고 제목도 짧게 줄인다 (2026-07-10부터 적용). 예: `output/기술블로그/2026-07/0710-반도체-드라이펌프`

**Step 2 — 글쓰기** (`블로그/agents/writer.md`)
- research.md + 블로그/guides/seo-guide.md + 블로그/guides/style-guide.md + 블로그/guides/company-info.md 기반
- 산출물: naver.md, google.md, meta.txt, faq.json, marketing.txt

**Step 3 — 이미지** (`블로그/agents/image-maker.md`)
- 이미지 소스 순서: 현장사진(1순위) → AI 생성(2순위)
- 재사용 금지: `블로그/output/used-images.json` 확인 후 미사용 사진만 선택
- 산출물: `블로그/output/[주제]/images/` 내 모든 이미지

**Step 3.5 — 블러 처리** (`블로그/blur_photo.py`) — 현장사진이 있을 때만
- `blur-config.json`에 펌프 좌표(`pump_box`) 기록 후 blur_photo.py 실행
- EXIF 회전 자동 보정 + 배경 블러 + 펌프 영역 복원
- 실행 후 반드시 Read 도구로 결과 이미지를 열어 시각 확인
- 블러 미확인 시 Step 4 진행 금지

**Step 4 — 품질 검수** (`블로그/check_quality.py` 직접 실행)
- `python check_quality.py "[주제폴더]"` 실행해서 현재 11개 항목을 검증한다.
- 검증 항목: final.md 글자수(최소 2,000자) · 메타설명 · 현장사진 · 사진용량 · EXIF 회전 · 펌프좌표 · GEO형식(## 스마텍 H2 금지) · 연락처중복 · 네이버글(최소 1,500자 등) · 표문법금지 · 사진개수대조.
- **하나라도 실패하면 해당 에이전트 재실행 후 check_quality.py 재실행**
- 글자수는 기존 검사기의 내부 기준이다. 2,000자를 채우려고 허구 사례·반복 문장을 넣지 않는다. 필요한 설명이 충분한데 길이만 미달하면 원인을 보고하고 기준 검토 전까지 발행을 보류한다.
- 자동 검사 통과만으로 사실·출처·사진의 정확성이 검증됐다고 간주하지 않는다. 공식 모델 자료·캡션·실제 파일을 직접 대조한다.
- 전체 통과 확인 후에만 Step 4.5 진행
- 결과는 `quality-log.jsonl`에 자동 기록됨

**Step 4.5 — 사진 승인** (업로드 전 필수 — 생략 불가)
- 품질 검수 통과 직후 반드시 아래 순서로 실행한다.

1. **사진 뷰어로 열기**: 아래 명령으로 현장사진과 썸네일을 윈도우 사진 앱에서 바로 연다 (터미널에서는 사진이 안 보이기 때문)
   ```
   Start-Process "블로그/output/[폴더]/images/field-1.png"   # 현장사진 (있을 때만)
   Start-Process "블로그/output/[폴더]/images/thumbnail.png" # 썸네일
   ```
2. **썸네일 표시**: Read 도구로 `블로그/output/[폴더]/images/thumbnail.png` 읽기
3. **현장사진 표시**: `images/field-1.png` 가 있으면 Read 도구로 읽기
4. **승인 요청 멘트** (항상 이 형식으로):
   ```
   📸 사진 확인해 주세요.
   - 썸네일: [위에 표시됨]
   - 현장사진: [위에 표시됨 / 없음]

   [폴더명]의 사진·원고를 [YYYY-MM-DD 예약 / 지금 발행]으로 진행할까요?
   괜찮으면 표시한 진행 방식에 대해 "OK"라고 해주세요.
   사진을 바꾸고 싶으면 원하는 수정을 말씀해 주세요.
   ```
4. **사용자가 사진·원고와 구체적 발행 방식·날짜를 승인한 뒤에만** 예약 승인 또는 Step 5 즉시발행 진행. 사진만 승인한 것을 즉시발행 승인으로 해석하지 않는다.
5. 사용자가 수정 요청 시 → 해당 이미지 재처리 → Step 4.5 다시 실행
- **주말 일괄 2편 모드**: 2편 모두 Step 4까지 완료 후 각 폴더명·썸네일·날짜를 보여주고 각각 예약 승인을 받는다.

## 주말 일괄 생성 모드 (선택 후 2편 작성·검수)

"다음주 주제 뽑아줘"는 후보 제시 요청이다. 후보만으로 전체 원고 생성·예약을 진행하지 않는다.

1. 후보 5개를 제시하고 사용자 2개 선택을 기다린다.
2. 선택한 2개를 Step 1~4 순서로 작성·검수한다. 각 편 완료 시 "1/2 완료", "2/2 완료"로 상태를 알린다.
3. 사진·원고를 보여주고 각각의 월·목 발행 날짜에 대해 예약 승인을 받는다.
4. 현재 주 미발행 글을 새 주 큐로 덮어쓰지 않는다. 미발행 글을 처리하거나 사용자와 이월을 정한 후 기존 큐 기록을 보존하고 교체한다.
5. `upload-queue.json`은 해당 주차와 정확한 날짜로 기록한다. 기본은 `approved: false`, `uploaded: false`이며, 해당 글·날짜의 예약 승인을 확인한 담당자만 `approved: true`로 바꾼다.

```json
{
  "_week": "2026-W38",
  "_created": "2026-09-13",
  "_note": "형식 예시. 실제 선택·검수·승인과 해당 날짜 확인 후 등록.",
  "day1": { "folder": "[카테고리/월/폴더명]", "title": "[제목]", "scheduled_date": "2026-09-14", "uploaded": false, "approved": false },
  "day2": { "folder": "[카테고리/월/폴더명]", "title": "[제목]", "scheduled_date": "2026-09-17", "uploaded": false, "approved": false }
}
```

완료 안내는 실제 상태만 표시한다: "[폴더명] — 월 YYYY-MM-DD 원고 검수 완료 / 사진·예약 승인 대기" 또는 "[폴더명] — 해당 날짜 예약 승인 완료". 원고만 만든 상태를 예약 완료로 부르지 않는다.

**예약 승인과 즉시발행 구분**: `approve_post.py`는 승인과 동시에 업로드하므로 미래 예약 승인에 사용하지 않는다. 자동 업로드는 승인된 큐를 Windows 작업 스케줄러가 해당 날짜에 처리한다. `auto_upload.py --dry-run`은 네트워크 요청 없이 일정·승인 상태만 확인한다.

## 반드시 지킬 것

- 단계별 담당자는 해당 `블로그/agents/*.md` 지침을 읽는다. 서브 에이전트를 사용할 때에는 범위와 파일 소유자를 정하고, 메인이 실제 산출물·검사 결과를 재확인한다.
- 도구가 지원되지 않으면 단계별 지침을 직접 수행하며, 존재하지 않는 Claude 명령·자동 기억이 작동한다고 보고하지 않는다.
- 사용자에게 중요한 발견·진행 상태를 알린다. 작업 결과·검증·미완료 상태는 `docs/astra_work_log.md`와 관련 저장소 메모리에 남긴다.
- 이전 발행 글 수정 시 현재 홈페이지 글 ID·본문을 확인하고 URL을 유지한다. 단순 날짜 변경·표현 치환을 성과 개선으로 포장하지 않는다.
- 출처를 숨기거나 전문가 경력·현장 사례·수치를 꾸며내지 않는다. 핵심 기술 주장에 제조사 공식 자료 링크와 적용 조건을 남긴다.

## 홈페이지 업로드 + 최종 안내 (Step 5)

모든 단계 완료 후 아래 순서로 진행한다.

### 1. 이미지 폴더 자동 열기
아래 명령으로 사진 폴더를 파일 탐색기에서 바로 연다:
```
explorer "C:\Users\rokmc\smartech\블로그\output\[카테고리]\YYYY-MM\[주제]\images"
```

### 2. 홈페이지 업로드
사용자가 Step 4.5에서 원고·사진을 승인하고 **지금 업로드하라고 요청한 한 폴더만** 처리한다. 먼저 큐 등록·날짜·이미 발행 여부를 확인한 뒤 approve_post.py를 실행한다:
```
python 블로그/approve_post.py "[폴더경로]"
```
approve_post.py는 upload-queue.json에 approved=true를 기록하고 upload_post.py를 **즉시 호출한다**. 미래 날짜 예약 승인이나 여러 글 일괄 승인 목적으로 사용하지 않는다.

### 3. 최종 안내 (항상 표시)
모든 작업이 끝나면 아래 형식으로 한 번만 표시한다. [주제], [id]는 실제 값으로 채운다:

```
✅ 완료!

🌐 홈페이지: https://www.smartechvacuum.com/blog/[id]
📝 네이버 복사: 블로그\output\[카테고리]\YYYY-MM\[주제]\naver.md
📁 사진 폴더: [실제 경로와 열기 성공 여부]
```

업로드가 막혔으면 원인과 실제 발행 여부를 먼저 확인한다. 성공 여부가 불명확한 상태로 재실행을 안내하지 않는다. 중복 여부를 확인했고 즉시발행 승인이 유효한 경우에만 아래 실행 안내를 제공한다:
```
⬆️ 홈페이지 업로드: 아래를 프롬프트에 붙여넣으세요
! C:\Users\rokmc\AppData\Local\Programs\Python\Python312\python.exe "C:\Users\rokmc\smartech\블로그\approve_post.py" "[주제]"
```

## 세션 마무리 자동 체크 (필수)

사용자가 종료 의사를 표현하면 ("여기까지", "저장해줘", "수고했어", "내일 이어서", "끝내자" 등)
아래 두 가지를 반드시 수행한다.

### 1. 에이전트 업데이트 체크

이번 세션에서 변경된 내용 중 아직 에이전트 파일에 반영 안 된 것이 있으면
해당 파일을 직접 수정한다. 없으면 "에이전트 업데이트 없음"으로 표시.

### 2. VS Code 알림 파일 작성

`C:\Users\rokmc\smartech\블로그\vscode-notify.md` 파일을 생성 또는 업데이트한다.
VS Code에 알려야 할 내용이 있으면 기록하고, 없으면 "없음"으로 표시.

```markdown
# VS Code 알림 — [날짜]

## 알릴 내용
- [항목]

## 없음
(없으면 이 줄만 표시)
```

파일 작성 후 사용자에게 안내:
"📋 VS Code에 알릴 내용을 vscode-notify.md에 저장했어요. VS Code 열면 확인해 주세요."
