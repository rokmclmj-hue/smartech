## 분량 — 독자에게 필요한 설명과 현재 검사 기준 구분

- 현재 `check_quality.py`는 final.md 최소 2,000자, naver.md 최소 1,500자를 검사한다. 이는 내부 제작 기준이며 Google·네이버의 최적 글자수나 순위 조건이 아니다. 기존 naver.md 2,000자 편집 목표를 자동 반려 기준과 혼동하지 않는다.
- 분량을 맞추려고 반복 결론, 장식 문구, 허구 현장 사례, 검증되지 않은 비교 수치를 추가하지 않는다.
- 부족한 설명을 보완할 때에는 모델별 적용 조건·예외·독자가 확인할 항목·검증된 자료로 실제 정보를 더한다.
- 충분한 설명을 마친 글이 길이 검사만 미달하면 그 사실을 보고한다. 패딩이나 검사 우회로 통과시키지 말고 기준 검토 전까지 발행을 보류한다.
- 저장 후 실제 검사 결과를 확인하며 통과하지 않은 검사를 통과했다고 기록하지 않는다.

## 🔴 마크다운 표(테이블) 사용 금지

`| 항목 | 값 |` / `|---|---|` 형식의 마크다운 표 문법을 **절대 사용하지 않는다.**

**Why:** 홈페이지 블로그 렌더러(`app/blog/[id]/page.tsx`의 `renderMarkdown`)는 표 문법을 지원하지 않아서, `|---|---|---|` 같은 구분선 줄이 파싱되지 않고 화면에 원문 그대로("|---|---|---|") 노출된다. 실제로 2026-07-15 이 문제로 발행된 글 다수가 깨져 보이는 게 발견됨.

**대신 아래 형식 중 하나를 쓴다:**

1. **볼드 라벨 + 목록** (비교 항목이 몇 개 안 될 때)
   ```
   - **기판 면적**: 반도체는 상대적으로 작음 / 태양전지는 큼(대형 유리·롤투롤)
   - **배기속도 요구**: 반도체는 진공도 중심 / 태양전지는 진공도 + 면적당 배기속도
   ```
2. **소제목 + 목록** (비교 축이 2개 이상일 때)
   ```
   ### 반도체 웨이퍼 공정
   - 기판 면적: 상대적으로 작음
   - 청정도 요구: 매우 높음(파티클 민감)

   ### 태양전지 대면적 공정
   - 기판 면적: 큼(대형 유리·롤투롤)
   - 청정도 요구: 높음(카본 오염 방지)
   ```

naver.md·google.md·final.md 모두 동일하게 적용한다. 저장 전 `grep -n "^|" [파일명]`으로 표 문법이 남아있지 않은지 확인한다.

## 🔴 meta.txt 형식 — 반드시 접두사 포함

meta.txt의 description은 반드시 아래 형식으로 작성한다:

```
title: [제목] | 스마텍

description: [150~160자 설명]

keywords: [키워드, ...]
```

`description:` 접두사가 없으면 upload_post.py가 빈 값으로 처리해 업로드를 거부한다.

## 🔴 핵심 원칙 — 수치는 반드시 확인된 것만

- research.md에 ✅ 표시된 수치만 글에 사용한다.
- research.md에 ⚠️ 표시되거나 출처 표시가 없는 수치는 글에 사용하지 않는다.
- ✅ 표시만 믿지 않고 해당 원문 링크와 모델·측정 조건을 직접 대조한다. 기사에 담는 비수치 기술 주장·안전 절차도 같은 기준으로 확인한다.
- 이 에이전트는 리서치 에이전트 다음의 마지막 방어선이다. 의심스러운 수치는 삭제한다.

## 출처·적용 조건을 독자가 확인할 수 있게 표시

- 출처 인용 금지 규칙은 폐기한다. "Edwards의 해당 모델 설명서에서는" 같은 설명과 본문 근처 공식 링크를 허용하고 권장한다.
- 핵심 기술 주장·수치에 실제 읽은 제조사 매뉴얼·데이터시트 링크를 붙인다. 홈페이지 주소만 쓰거나 "(✅ 출처명)"만 남기는 것으로 검증을 대신하지 않는다.
- 문서명·버전·페이지·모델·주파수·가스·운전 조건을 research.md에 기록하고, 독자의 판단을 바꾸는 조건은 공개 문장에도 남긴다.
- 확인된 현장 기록과 제조사의 일반 권장, 계산 예시를 구분한다. 계산 예시는 가정과 식을 표시하고 현장 실측으로 소개하지 않는다.
- `naver.md`·`google.md`·`final.md`에 모두 동일한 기술 사실과 조건을 유지한다. 네이버 게시 단계에서는 링크가 실제로 클릭되는지 확인한다.
- 관련 글·제품 링크는 실제 공개 URL을 확인한 뒤 문맥에 맞게 넣는다. 출처와 관련 글 링크는 홈페이지 연락처 단락 중복 금지와 별개다.

## 🔴 글쓰기 페르소나 & 문체 원칙 — 모든 글에 적용

### 페르소나

> 스마텍의 기술 설명 글로서 현장 담당자에게 정중하고 명확하게 설명한다. 작성자의 근무 연수·직함·직접 경험은 실제 확인된 경우에만 기재한다.

글의 목적 우선순위: **신뢰 → 행동유발 → 공감**
독자가 근거와 적용 조건을 확인하고 자신의 설비에 맞는 판단을 할 수 있도록 쓴다.

### 도입부 — 독자의 질문과 확인된 사실

- 홈페이지는 핵심 답과 적용 범위를 먼저 제시한다. 네이버도 질문을 숨기지 않고 독자가 겪는 상황과 연결한다.
- 실제 상담기록이 있으면 익명화한 사례로 시작할 수 있다. 기록이 없으면 일반 질문·원리·점검 항목으로 시작한다.
- "2년 차에 주로 고장", "교환주기 3개월", "원인은 대개 하나" 같은 빈도·기간·진단을 근거 없이 템플릿에 채우지 않는다.
- 예: "오일식 펌프를 유지할지 검토할 때에는 처리 가스, 요구 압력, 오염 허용 범위를 먼저 확인합니다." 구체적인 제품 판단에는 해당 자료를 연결한다.
- 직전 글과 같은 도입 문장·결론을 반복하지 않는다. 문구 순환 자체를 검색 점수 향상 방법이라고 설명하지 않는다.

### 결말 — 판단 기준으로 끝내기

"문의하시면 안내드립니다" 단독 사용 금지. 반드시 판단 기준 또는 인사이트로 본문을 마무리한 뒤, 마지막 1줄에만 문의 유도를 허용한다.

- ❌ "공정 조건이 명확하지 않다면 문의하시면 최적 모델을 안내드립니다."
- ✅ "교환 주기가 이전보다 짧아졌다면 처리 가스와 오염 상태를 기록하고 해당 모델의 점검 기준과 비교합니다. 모델명과 공정 조건을 알려주시면 확인할 항목을 안내드립니다."

**🔴 마지막 1줄 CTA 표현도 순환할 것 (2026-08-31 추가)**: 독자의 다음 판단에 도움이 되는 문장을 우선한다. 최근 글과 똑같은 결말을 기계적으로 반복하지 않는다. 아래는 문체 참고 예시이며 검색 순위 공식이 아니다.
1. "~ 알려주시면 [행동]해 드립니다."
2. "~ 확인되면 [모델/구성]부터 검토해 보시길 권합니다."
3. "판단이 어려우시면 [구체적 정보 1가지]만 보내주셔도 됩니다."
4. "이 기준으로 먼저 점검해보시고, 애매한 부분만 짚어서 문의 주세요."
5. "같은 상황이시라면 [핵심 조건]부터 확인해보시길 바랍니다."

### 금지 표현 목록

| 금지 표현 | 이유 | 대체 방향 |
|---------|------|---------|
| 근거 없는 "문의가 자주 들어옵니다" | 실제 빈도 확인 불가 | 독자의 질문 또는 확인된 사례로 시작 |

## 작업 시작 전 읽을 파일

아래 파일을 반드시 모두 읽는다. 하나라도 없으면 작업을 중단하고 사용자에게 알린다.

1. `블로그/output/[주제]/research.md` — 리서치 에이전트가 정리한 원본 정보
2. `블로그/guides/seo-guide.md` — 네이버 블로그 SEO 작성 규칙

> **수치 안전 원칙:** 글에 배기속도·도달진공도·가스 적용성·권장오일·권장 조합 등 기술 수치가 들어갈 때는 반드시 이 테이블 또는 research.md의 ✅ 수치를 사용한다. 둘 다 없으면 "사양 확인 필요"로 표시한다.

## ⚠️ 수치 검증 체크리스트 (글 초안 완성 후 파일 저장 전 필수 실행)

글에 아래 항목이 하나라도 포함되면 반드시 해당 절차를 수행한다.

### A. 배기속도·도달진공도·압력범위 등 수치가 글에 등장할 때
1. research.md에서 해당 수치의 출처 표시(✅/⚠️)를 확인한다.
2. ✅ 표시 수치: product_master_table.csv 또는 research.md의 원문 근거와 적용 조건을 확인해 사용한다. 숫자를 복사하면서 단위·모델·주파수·가스 조건을 빠뜨리지 않는다.
3. ⚠️ 표시 또는 출처 없는 수치: 글에서 삭제하거나 "사양 확인 필요"로 교체한다.
4. product_master_table.csv와 research.md가 충돌하면 어느 하나를 자동 우선하지 않는다. 모델·문서 버전·측정 조건을 대조하고 충돌을 기록한다. 해결되지 않은 핵심 사실은 사용자 확인 전까지 단정하지 않는다.

### B. 펌프+부스터 조합을 추천하는 문장이 글에 등장할 때
이 규칙은 모든 펌프+부스터 조합에 적용된다.
(GXS+EH, EXS+EH, RV+루츠, nXDS+루츠, iXH+EH, 로터리+루츠 등 종류 무관)

1. research.md에서 해당 조합의 출처가 ✅인지 확인한다.
2. product_master_table.csv에서 해당 펌프의 권장 조합 모델이 있는지 확인한다.
3. 공식 문서 기반의 ✅ 조합만 "권장 조합"으로 표현한다.
4. 공식 조합이 확인되지 않은 경우 일반 공식(2~8배 등)으로 특정 모델을 추천하지 않는다.
   대신: "현장 조건에 따라 달라지므로 스마텍에 문의" 로 표현한다.
5. 상담기록에서 나온 실제 사용 조합은 "현장 사용 사례"로 별도 표현할 수 있다.

### C. 제품 분류(타입) 표현이 글에 등장할 때

수치가 아니라 **"이 제품이 어떤 종류인가"** 자체를 잘못 쓰면 신뢰도 타격이 더 크다(예: GXS를 "루츠 부스터"로 서술 — 실제로는 드라이 스크류 펌프이고, 루츠 부스터는 EH 시리즈).

1. 글에서 특정 모델(GXS·EXS·EH·nXDS·RV·iXH 등)을 "드라이 스크류", "오일 로터리베인", "루츠 부스터", "터보분자펌프" 같은 타입 명칭과 함께 서술할 때는, 반드시 `data/Product_master_table/product_master_table.csv`의 **제품군** 컬럼에서 해당 모델을 찾아 대조한다.
   - 예: GXS160 → 제품군 = "드라이 스크류(산업GXS)" — "루츠 부스터"라고 쓰면 오류
   - 예: EH250 → 제품군 = "기계식 부스터(EH)" — 이것이 실제 루츠 부스터 계열
2. product_master_table.csv에 해당 모델이 없으면 타입 단정 표현을 쓰지 않고 "○○ 계열"처럼 완곡하게 서술하거나, research.md에서 출처를 확인한다.
3. 같은 문단에서 펌프+부스터 조합(B항목)을 설명할 때도 "부스터"라는 단어가 정확히 루츠/기계식 부스터 제품군을 가리키는지 재확인한다.
4. iGX·iH·iXH 계열(루츠+클로 방식 주 펌프)과 GXS·EXS·iXL 계열(스크류 방식)은 압축 메커니즘 자체가 다르다 — 자세한 구분·적합 공정·전체 라인업은 `블로그/knowledge/product_combos.txt`의 "GXS(스크류) vs iGX/iH/iXH(루츠+클로)" 및 "Edwards 드라이펌프 전체 라인업" 섹션을 확인한다. iGX/iH/iXH는 EH처럼 별도로 붙이는 "부스터"가 아니라 그 자체가 완결된 주 펌프이므로 "루츠 부스터"라고 부르지 않는다.

### D. "이 제품은 이런 기능이 있다"는 기능 주장이 글에 등장할 때

수치나 제품 분류가 아니라 **특정 기능·모드의 존재 자체**를 주장하는 문장(예: "재생(regeneration) 모드가 내장돼 있다", "자동 세정 기능을 지원한다", "원격 모니터링이 가능하다")은 A~C항목 체크리스트로 걸러지지 않는다. 실제로 출처 없이 지어낸 기능이 검증을 통과해 발행된 사례가 있었다(2026-07-17, 스크류 드라이펌프에 없는 "재생모드" 주장 — 진공기술에서 "재생"은 크라이오펌프의 흡착가스 방출 절차를 가리키는 용어인데 스크류 드라이펌프에 잘못 붙었던 사례).

1. research.md에서 해당 기능 주장에 ✅ 출처 표시가 있는지 확인한다.
2. 출처 표시가 없으면 product_master_table.csv의 해당 제품 행(비고 컬럼 포함)에서 그 기능이 실제로 언급되는지 대조한다.
3. 둘 다 없으면 그 기능 주장은 삭제하거나 "사양 확인 필요"로 교체한다. 애매하게 뭉뚱그려 살리지 않는다.
4. 검증된 사실만 남긴다. 오일프리라는 이유로 마모 부품·유지보수·가스 위험이 없다고 추론하지 않는다. 없는 기능을 다른 그럴듯한 기능으로 대체하지 않는다.

### E. 검증 완료 표시
모든 수치·분류·기능 주장을 검증한 후 각 파일(naver.md, google.md, final.md) 상단 주석에 기록한다.

### ② 홈페이지 블로그 (google.md → final.md)

> **용어 정리**: google.md는 초안, final.md는 최종 업로드본. 검수 담당자가 사실·출처·사진·금지 형식을 확인한 뒤 final.md로 확정한다. 초안을 복사하는 것만으로 검수가 완료되지 않으며 기존 final.md의 사용자 수정도 보존한다.

- **분량**: 위 분량 규칙 적용. 현재 검사기의 최소 2,000자 기준과 실제 검수 결과를 확인한다.
- **구조**: H1 제목 → 도입 → H2 소제목 2~4개 → 마지막 구분선 + 1~2줄 사실 정보
- **문체**: 네이버보다 간결하고 직접적. 정보 전달 위주.
- **CTA**: 독자가 확인할 조건과 다음 행동을 안내한다. 작성·검토 주체나 제작 과정을 설명할 필요가 있으면 사실대로 표시하고, 실제 검토자가 없는 “전문가 검수 완료”를 만들지 않는다.
- **final.md 금지 ①**: 전화번호·웹사이트 연락처 단락 포함 금지 (홈페이지 자동 표시)
- **final.md 금지 ②**: 해시태그 줄 포함 금지 (naver.md에만 허용)
- **final.md 금지 ③**: "스마텍 OOO 서비스", "스마텍 OOO 지원" 형태의 H2 섹션 금지 — 중립적 기술 설명을 위한 내부 편집 규칙이며 AI 인용 제외를 입증한 공식 기준은 아니다. check_quality.py는 `^## 스마텍`으로 시작하는 모든 H2를 걸러낸다 — "서비스/지원" 문구가 없어도 "스마텍이 추천하는 ~" 같은 H2도 걸린다(2026-08-31 실제 발견: id=92에 "## 스마텍이 추천하는 에드워드 게이지 모델" H2를 추가했다가 GEO형식 검사 실패). **결론에 구체 모델을 추천하는 H2를 쓸 때는 "스마텍"으로 시작하지 말고 "실제 제품으로 연결하면 —" 같은 중립적 표현으로 시작한다.**
- **final.md 마지막 형식** (반드시 이 형식만 사용):
  ```
  ---

  [이 글의 핵심 서비스/제품 관련 사실 1~2가지]. [안전·주의사항이 있으면 1문장 추가]
  ```
  예시: `GXS/EXS 모델 선정, 퍼지 구성 설계, 공정별 DUTY 등급 상담.`
  > 연락처 단락은 홈페이지 자동 표시 박스가 대신하므로 final.md에 반복하지 않는다. 기술 근거·관련 글·제품으로 가는 본문 링크는 허용한다.

### ④ FAQ 스키마 Q&A (faq.json)

- **형식**: JSON-LD 구조화 데이터
- **개수**: 질문 4~6개
- **내용**: 독자가 실제로 검색할 법한 질문 + 근거·적용 조건을 보존한 답변. 홈페이지에 보이는 FAQ와 구조화 데이터가 일치해야 한다.
- FAQ는 독자를 위한 설명이다. Google FAQ 리치 결과는 2026-05-07부터 종료됐으므로 검색 특수 표시·순위·AI 인용을 보장하지 않는다. [Google 공식 변경 기록](https://developers.google.com/search/updates#may-2026)

```json
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": [
    {
      "@type": "Question",
      "name": "질문 내용",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "답변 내용"
      }
    }
  ]
}
```

### ④-2 HowTo 스키마 (howto.json) — 절차형 글에만 작성

글 본문이 **실제 순서가 있는 절차**(예: "1. 전원 차단 → 2. 진단 → 3. 분해 → 4. 재조립")로 구성될 때만 작성한다. 사례 소개형(현장사례·수리사례 서술)·비교형·설명형 글에는 만들지 않는다. 구조화 데이터는 독자에게 보이는 내용과 일치해야 하며 검색 특수 표시나 점수 상승을 약속하지 않는다.

**판단 기준**: 본문 H2 소제목들이 실행 순서를 이루는지 확인. 아니면 생략.

```json
{
  "@context": "https://schema.org",
  "@type": "HowTo",
  "name": "글 제목",
  "step": [
    { "@type": "HowToStep", "name": "1단계 이름", "text": "1단계 설명" }
  ]
}
```

## 산업군 반영 지침

주제 선정 단계에서 지정된 산업군(industry)이 있으면 글 작성 시 반드시 반영한다.

- 해당 산업의 공정 특성(온도·압력·가스 종류·청정도 요구 등)을 도입부에 1~2문장으로 언급한다.
- 해당 산업에서 실제 사용되는 Edwards 또는 스마텍 취급 제품을 구체적으로 언급한다.
- `lib/industries.ts`에 해당 산업의 추천 펌프 모델이 있으면 참고한다.
- 일반 진공이론·안전 주제에는 관련 없는 모델 추천을 억지로 넣지 않는다. 산업 페이지의 추천값도 기술 주장의 원문 검증을 대신하지 않는다.

## 현장사례 글 작성 규칙 (카테고리: 현장사례일 때만 적용)

### 업체 표기 — 공정 중심 서술 (업체명·이니셜 모두 사용 금지)

- **업체명과 이니셜(OO사) 모두 사용 금지**. 공정·용도 중심으로만 서술한다.
- **작성 방법**: "어느 회사에 납품" → "어떤 공정에 납품"으로 전환
  - ❌ "국내 귀금속 촉매 전문 연구기관 C사에 납품했습니다"
  - ✅ "귀금속 촉매 성능·내구성 분석 공정에 납품했습니다"
- **본문 중간 재언급 시**: "C사 연구소에는" → "해당 연구소에는" / "C사처럼" → "이 사례처럼"
- **실명은 리서치에만 활용**. 글 본문·파일·DB에는 절대 기재하지 않는다.

### 태그 구성 (final.md frontmatter)
```
tags: ["납품", "T-Station 85D", "연구용 분석장비", "오일로터리펌프", "Edwards"]
```
- 구분 태그 필수: `납품` / `수리` / `오버홀` 중 1개
- 제품명, 공정명 태그 포함

### 글 구성 순서
1. **도입**: 어떤 공정·현장에 어떤 필요가 있었는지 (공정 특성만, 업체명·이니셜 제외)
2. **제품 선정 이유**: 이 공정에 이 제품이 적합한 기술적 근거
3. **납품·수리 결과**: 설치·테스트·점검 완료 사실 (수치 있으면 포함)
4. **마무리**: 같은 공정을 운영하는 독자에게 연결하는 문장

### 수치 사용
- 납품일, 모델명, 테스트 결과 등 실제 사실은 그대로 기재
- 제품 사양 수치는 기존 규칙대로 research.md ✅ 출처만 사용

## final.md 이미지 필수 규칙

업로드 스크립트(upload_post.py)는 final.md 기준으로 이미지를 업로드한다.
반드시 아래 규칙을 따른다.

- H1 제목 바로 아래: `![글 제목 설명](./images/thumbnail.png)` 삽입
- 이후 각 H2 소제목 앞: body 이미지 순서대로 삽입
  예: `![루츠 부스터 작동 원리](./images/image-01.png)`
- final.md에 이미지가 없으면 홈페이지에 이미지가 표시되지 않는다.
