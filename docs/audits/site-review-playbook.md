# 스마텍 홈페이지 정기 심층 점검 지시서 (초안 v0.1, 2026-10-21)

> 이 파일 하나로 매달 같은 방법의 점검을 반복한다. 사람·AI 누가 돌려도 결과를 지난번과 비교할 수 있게 하는 것이 목적이다.
> 출발점: 2026-10-21 외부 심층 진단(사실 지적 거의 모두 맞음) → [확인 결과](2026-10-21-external-deep-review-check.md).
> 우리가 놓쳤던 것: 지금까지 점검은 "있는지"만 봤고 **"맞는지·서로 같은지"**는 보지 않았다.

## 0. 점검 주기

| 주기 | 이름 | 방법 | 결과 |
|---|---|---|---|
| 매주 | 기계 점검 | 정답이 정해진 항목만 스크립트로(아래 4장). 아직 스크립트 없음 — 1~2회 수동 실행 후 만든다 | 문제가 있을 때만 알림 |
| 매달(첫 주) | 심층 점검 | 이 지시서 1~3장 전체를 AI가 실행 | `docs/audits/YYYY-MM-DD-monthly-review.md` |
| 분기 | 전체 점검 | 심층 점검 + 표본을 넓혀 전 페이지·전 블로그 | 같은 형식 |
| 큰 수정 후 | 로컬 코드리뷰 | `/code-review medium origin/reviewed` | reviewed 전진 |

## 1. 지켜야 할 원칙

1. **확인·추론·미검증을 나눈다.** 직접 열어 본 것만 "확인"이다. 순위 하락·AI 인용 실패·문의 이탈은 측정하지 않았으면 단정하지 않는다.
2. **비회원 상태로 본다.** 공개 HTML(첫 응답)과 브라우저가 그린 화면을 둘 다 본다. 관리자 로그인 화면은 원가(배율 1.00)가 보이므로 고객 화면으로 착각하지 않는다.
3. **원본과 대조한다.** 사양 숫자는 `public/catalogs/*.pdf`의 **행 이름까지** 맞춘다(10/21 사례: Peak 칸에 Displacement 값).
4. **같은 내용은 모든 곳에서 같아야 한다.** 제품 표 ↔ 모델·SKU 설명문 ↔ 블로그 ↔ FAQ ↔ JSON-LD ↔ llms.txt.
5. **같은 기능은 모든 화면에서 같게 동작해야 한다.** 한 화면을 바꾸면 같은 기능을 쓰는 다른 화면도 본다(10/20 비회원 카트 도입 때 파트번호 화면 누락 사례).
6. **점검은 보고서만 만든다.** 코드·DB 수정은 대표님 "ok" 후에만. 공개 응답에 원가·내부정보가 보이면 즉시 보고.
7. **처방은 가장 작은 방법부터.** "재설계"는 같은 오류가 여러 곳에서 반복될 때만 제안한다.

## 2. 점검 항목 (8가지 렌즈)

각 항목은 "어떻게 확인하나 → 무엇이 정답인가"로 적는다. 결과는 3장 형식으로 기록한다.

### 2-1. 사양 숫자 ↔ 카탈로그
- `lib/product-specs.ts` 각 분류에서 **매달 2개 분류를 돌아가며** 카탈로그 PDF 표와 칸별 대조(배기속도·도달압력·온도·플랜지·무게). 행 이름(Peak / Displacement / 50·60Hz)까지 확인.
- 순서: 1월 RV·E2M소형 → 2월 E2M중대형·E2S → 3월 nES·nXDS → 4월 XDS·GXS → 5월 EXS·iXH → 6월 iXL·nXRi → 7월 nEXT·EH → 반복.
- 같은 값이 쓰이는 곳: 모델 화면 설명문(`modelSeoText`), 홈 제품 창 스펙 비교, 블로그 본문(DB 검색).

### 2-2. 화면 ↔ 검색엔진용 데이터(JSON-LD)
- 블로그: 모든 FAQPage 질문이 화면에 보이는지, articleBody가 본문 전체이고 사진 주소가 없는지.
- 파트번호 화면: Product.offers availability(InStock/OutOfStock/Discontinued)와 화면 재고 문구가 같은지, 가격이 같은지.
- 산업 페이지 FAQ, 회사 소개 FAQ도 표본 확인.

### 2-3. 글 내용의 근거 범위
- 제목·FAQ가 본문보다 강하게 말하지 않는지("쓸 수 없다" vs 본문 "적용 분야가 다르다").
- 숫자에 **단위**가 있는지, 시뮬레이션 1건 결과를 조건 없이 일반화하지 않았는지.
- 진공 구간 용어: ISO 3529-1:2019 기준 고진공 0.1~10⁻⁶ Pa(10⁻³~10⁻⁸ mbar), 그 아래 초고진공. 극초고진공은 10⁻¹² mbar 미만(글 74 설명).
- 출처는 "글당 1~2곳·Edwards 자료만" 규칙 위반 여부도 함께.

### 2-4. 고객 4유형 경로 따라가기 (비회원, 휴대폰 390px)
| 고객 | 출발 | 끝까지 가야 하는 곳 |
|---|---|---|
| 같은 모델 재구매 | 구글 → 파트번호 화면(예: A65501903) | 재고/납기 확인 → 견적 담기 → 카트 → 주문 요청 화면 |
| 사례 보고 교체 | 블로그 현장사례(예: 104) | 같은 제품 화면 또는 견적 문의, 관련 글이 비슷한 사례인지 |
| 고장 수리 | /repair | 접수 방법·보증·시험 근거·최근 사례 |
| 새 공정 선정 | 산업 페이지 | 추천 계열 → 모델 버튼 → 모델 화면 → 파트번호 → 담기, 펌프 선정 계산 |
- 끊기는 곳(로그인 요구, 다른 동작, 빈 화면, 같은 글만 반복)을 기록한다. 실제 제출은 하지 않는다.

### 2-5. 검색로봇이 갈 수 있는 길
- robots.txt, sitemap 개수(모델·SKU·블로그·산업), 첫 HTML에 링크가 있는지(`/products` 목록은 브라우저에서만 그려짐 — 알려진 한계).
- 모델 페이지로 들어오는 내부 링크 수(산업 페이지 기준 10/21 323개). 크게 줄면 원인 확인.
- canonical·리디렉션·404·noindex 표본, smartech-opal.vercel.app canonical.

### 2-6. 분류·추천
- 블로그 탭별 글 수, 새 글의 분류·태그가 탭과 관련 글 규칙에 맞는지(공통 태그만 단 글은 관련 글이 최신순으로 떨어짐).
- 관련 글 표본 5편이 실제로 비슷한 주제인지.

### 2-7. 공개 정보 보호
- `node scripts/check-public-leaks.mjs`(라이브). 비로그인 `/api/products` 응답에 costPrice·listPrice·supplierName 없는지.

### 2-8. 방향성 (판단 항목 — 의견으로만)
- 대리점만 가진 근거(수리 사례 수치·출고 시험·납품 사례)가 제품·산업 화면 가까이에 있는지.
- 새로 늘어난 페이지·글이 구매 판단으로 이어지는지.

## 4. 매주 기계 점검 후보 (스크립트로 만들 항목)

정답이 정해져 있어 사람 판단이 필요 없는 것만:
1. 사양표 전 값 ↔ 카탈로그 추출 텍스트 자동 대조(행 이름 포함)
2. 블로그 전 글: FAQ 질문 화면 표시·FAQPage 형식·articleBody에 http 없음
3. 파트번호 표본: 비회원 담기 버튼·재고 문구 ↔ availability
4. 산업 21페이지 모델 링크 수·링크 200 여부
5. leak-check 라이브
6. sitemap 개수 변화

→ 10/23 전후 월간 점검 때 수동으로 한 번 돌려 본 뒤, 대표님 승인 받아 스크립트 + Windows 예약 작업으로 만든다(새 패키지 없이 기존 node·playwright).
